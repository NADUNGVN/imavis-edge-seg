# Calibrated visual-risk router v1 (Contribution 3) — 2026-09-14

Implemented `src/imavis_edge_seg/router/`: the first code for Contribution 3, which
had been at 0% (only its calibration-metric prerequisite,
`evaluation/calibration.py`, existed before this).

- `risk_probe.compute_risk_score(logits, target=None)`: per-image mean softmax
  entropy from one cheap pass (typically the "tiny" level) -- no separate trained
  probe network needed. `target` is accepted so a *fitting*-time caller can compute
  the score over exactly the pixels its observed error was also computed over;
  omitted at real inference time (no ground truth available then).
- `calibrator.fit_risk_calibrator(raw_scores, errors)`: quantile-binned, monotonic
  (cumulative-max enforced) mapping from raw entropy to expected error, fit on
  validation data only (`RESEARCH_PLAN.md` §5's explicit requirement -- never fit on
  test data).
- `policy.select_level(candidates, config, ...)`: implements all 5
  `RouterConfig.strategy` options (`static_small`, `static_large`, `oracle`,
  `entropy`, `calibrated_risk`), reusing `search.pareto.ParetoPoint` for the
  candidate (level, cost, quality) tuples on one deployment target.

17/17 new tests pass (111/111 total): risk score correctly ranks confident vs.
uniform predictions and excludes `IGNORE_INDEX` pixels; calibrator rejects
empty/mismatched input, tracks a true score-error relationship through noise, and
stays monotonic even against a deliberately non-monotonic synthetic input; every
policy strategy is tested including the two error-handling paths (missing risk
argument, unknown strategy).

## Explicit scope limits (documented in the modules, not hidden)

- **One risk estimate per image, not per candidate level.** The `_select_by_risk`
  escalation ("how many levels to step up above `risk_target`") is a simple
  proportional heuristic, not a calibrated per-level decision -- refining this needs
  either a risk estimate conditioned on each candidate level, or calibration data
  relating the cheap-level score to *each other* level's expected error. Neither
  exists yet.
- **Calibrator is quantile-binned + cumulative-max, not full isotonic regression**
  (no new dependency added) -- documented as correcting small-sample noise in an
  already-roughly-monotonic signal, not fixing a fundamentally broken one.
- **No real risk-vs-error data has been fit yet.** `fit_risk_calibrator` has only
  been tested on synthetic data. A real calibrator needs `compute_risk_score` run
  over an actual validation set (Cityscapes/ACDC val) alongside each image's real
  per-image error, which hasn't been assembled.
- **Not wired into evaluation or deployment.** No script computes real risk scores
  from the trained supernet, fits a real calibrator, or measures router
  overhead/AURC/selective-mIoU end to end yet -- this is the decision logic and its
  unit-level correctness, not a running system.

## Update 2026-09-15: `scripts/evaluate_router.py` — wired into a real eval pass

Added `router/observed_error.py` (`compute_per_image_error`: per-image pixel
misclassification rate, masked the same way `risk_probe.compute_risk_score`'s
`target`-given branch is, so a calibrator's (raw_score, error) pairs are computed
over matching pixels) and `RiskCalibrator.to_dict`/`from_dict`/`save`/`load` (JSON)
for persisting a fitted calibrator.

`scripts/evaluate_router.py` closes 3 of the 4 items below at once: it splits each
val split's images in half by alternating index, fits a real calibrator on one half
(with ground truth, as §5 requires -- calibration only ever fit on validation data,
and never on the same images used to score a policy), then actually runs every
candidate level's forward pass on the other, held-out half and routes each image
per-image under `static_small`/`static_large`/`entropy`/`calibrated_risk` (+
`oracle` given `--eval-json`) using *only* the probe-level risk score (no ground
truth, matching real inference) -- accumulating each strategy's real *achieved*
mIoU and average real latency (joined from `outputs/benchmark_lookup_table.csv`,
real E1/E3 hardware measurements) from its actual per-image choices. This is the
real RQ3 comparison, not just the unit-level policy logic tested on 2026-09-14.

Verified before shipping with a synthetic tiny supernet + monkeypatched loaders
(random weights/labels, 6 images) exercising the full fit/route/accumulate flow end
to end without error -- this validates the *plumbing*, not real accuracy; no GPU or
real Cityscapes/ACDC data is available on this dev machine.

## Update 2026-09-15, same day: first real run (SERVER-02, `pace_seg_v1_aug_seed0`,
Cityscapes, E3/tensorrt_gpu) -- caught and fixed a real scale-mismatch bug

| strategy | avg latency (ms) | achieved mIoU |
|---|---|---|
| static_small | 0.941 | 0.3003 |
| static_large | 9.414 | 0.5238 |
| entropy | 6.611 | 0.5032 |
| calibrated_risk | 1.307 | 0.3481 |
| oracle | 9.414 | 0.5238 |

First reaction: `entropy` looks better than `calibrated_risk` (0.5032 vs. 0.3481
mIoU). But `entropy` spends 6.611ms -- 96% of `static_large`'s 9.414ms -- while
`calibrated_risk` spends only 1.307ms. Normalizing to mIoU gained per extra ms
above `static_small`'s baseline: `calibrated_risk` = 0.131 mIoU/ms vs. `entropy` =
0.036 mIoU/ms -- **`calibrated_risk` is ~3.6x more efficient per unit of extra
latency**; `entropy`'s higher absolute mIoU comes from spending almost as much as
`static_large` does, not from smarter per-image decisions.

Root cause: `entropy`'s raw risk (softmax entropy in nats, ~0.3-3 typical range)
and `calibrated_risk`'s calibrated risk (an error probability, 0-1) are different
scales, but the script's first version compared both against one shared
error-scale `risk_target` (~0.15, the fit-half's mean observed error). Dividing
`entropy`'s nats-scale score by an error-scale target gives a huge
`overshoot_ratio`, so `_select_by_risk` (`router/policy.py`) nearly always
escalates to the most expensive available level regardless of the actual
per-image signal -- explaining why `entropy`'s average latency (6.611ms) sits so
close to `static_large`'s. **Fixed same-day**: each strategy's default
`risk_target` is now auto-picked from the fit-half's mean *on that strategy's own
scale* (`entropy` -> mean raw score; `calibrated_risk` -> mean observed error), so
the two are no longer compared through a scale that only makes sense for one of
them. **Fixed again 2026-09-16**: split the one `--risk-target` CLI flag into
`--error-risk-target` (calibrated_risk's scale) and `--raw-risk-target` (entropy's
scale) -- a single shared override flag would have let a sensitivity sweep
reintroduce this exact bug (passing one error-scale value to override both).

Kept above as the record of the bug, not a real result.

## Update 2026-09-15, later same day: re-run with the fix -- fair result, first real
RQ3 evidence

| strategy | avg latency (ms) | achieved mIoU |
|---|---|---|
| static_small | 0.941 | 0.3003 |
| static_large | 9.414 | 0.5238 |
| entropy | 1.246 | 0.3378 |
| calibrated_risk | 1.307 | 0.3481 |
| oracle | 9.414 | 0.5238 |

Reproduced identically across 2 independent runs (deterministic: fixed val split,
no eval-time randomness). With the scale fix, `entropy` and `calibrated_risk` now
land at nearly the same latency (1.246ms vs. 1.307ms, +0.061ms) -- a genuine,
apples-to-apples comparison. **`calibrated_risk` wins**: +0.0103 mIoU (0.3481 vs.
0.3378) for that +0.061ms. Normalized to mIoU/ms above `static_small`'s baseline:
`calibrated_risk` = 0.1306, `entropy` = 0.1230 -- `calibrated_risk` is modestly
more efficient (~6% higher mIoU/ms), a real but small effect, not the 3.6x the
pre-fix (buggy) numbers implied.

**First real evidence for RQ3's actual claim** (calibrated routing beats
entropy-only routing) -- on one split (Cityscapes), one target (E3/tensorrt_gpu),
one architecture (the shared supernet). Both policies still leave most of the
`static_small` -> `static_large` accuracy gap (0.3003 -> 0.5238) unused at this
auto-picked `risk_target` (0.1472, the fit-half's mean observed error) -- neither
strategy escalates to `medium`/`large` often for these Cityscapes images, so this
result mainly speaks to the *low-risk-target* regime; how the two compare at a
stricter `risk_target` (forcing more escalation) is untested.

## Not yet done

- **Broader coverage**: ACDC (adverse conditions -- the harder, more
  policy-relevant regime) and E1/Hailo not yet run, only E3/Cityscapes.
- **Risk-target sensitivity**: only the auto (fit-half mean) `risk_target` has been
  tried; a stricter target that actually forces escalation to `medium`/`large`
  sometimes is untested and would show whether `calibrated_risk`'s edge holds,
  grows, or shrinks outside this low-escalation regime.
- Wire `select_level` into an actual *streaming* multi-engine inference loop (§5.3:
  switch engines on an 8-32 frame window, not per-image as the eval script does --
  the eval script measures per-image routing quality, not the windowed amortization
  scheme itself).
- Router-overhead measurement against the §11 Go bar's specific "<~5% of
  end-to-end cost" framing (the eval script's avg-latency-per-strategy is a related
  but not identical number -- it's the cost of the *chosen* level, not the added
  cost of the probe pass itself as a fraction of total pipeline cost).
- Per-level (not just per-image) risk conditioning -- still the documented MVP
  limitation from 2026-09-14.
- UIoU (needs ACDC's uncertain-region annotations, not wired into the dataset
  loader).
